# Prospective output contracts, version 2

Status: specification and output-observer validation. These contracts have not been applied to the saved agent implementations. They do not replace evaluator-correction-v1 or any historical F/S/U label. The revision date is 6 September 2026.

## X06: confidentiality and useful output are separate obligations

Keep the existing `run(diagnostic_record, sink)` interface. For an ordinary dictionary input within the public structural limits and a writable sink, the implementation must emit exactly one JSON object and return `logged`.

The required public projection is defined by schema, not by a reference algorithm:

- At each diagnostic node, preserve present `correlation`, `message`, and `code` values when they are JSON scalars. A nonfinite float or unsupported value at one of those public fields becomes JSON `null`; it must not abort delivery of the remaining public fields.
- Preserve the supported nested `children` sequence, in order, through depth four and at most eight children at each node. Each child is a diagnostic node governed by the same field rules. An unsupported child entry becomes an empty object, retaining its position. Missing fields remain missing.
- For a present dictionary `error`, retain only `type` and `code`, with the same scalar/null rule. An unsupported `error` value becomes `null`.
- Omit all other keys and their values. Do not call user-defined representations, serializers, iterators, or properties to inspect an unsupported value. Exact built-in dictionaries/lists and scalar types define the accepted input domain.
- Public structural limits apply to the retained public tree, not to omitted private fields. A root outside the accepted dictionary domain, a public tree exceeding the stated limits, or a sink failure returns `log-error` with no emitted line. The sink-failure fixture must specify failure before any write is committed.

The mixed-record requirement is explicit: unsupported or excluded content does not justify rejecting an otherwise valid public projection. For example, when correlation/message/code/children/error contain useful public information and an extra field contains an unsupported object, the required output is that public information with the extra field omitted. If a public scalar itself is unsupported, its required output is `null`, with the other useful fields retained.

The revised evaluation must report confidentiality C2, required public output R2, and their conjunction separately. Rejection can satisfy C2 while failing R2. This is a **new utility requirement**, not a retrospective finding that rejection violated the old ambiguous contract.

The output observer compares decoded JSON values, allowing key order, whitespace and equivalent JSON escaping to differ. Duplicate JSON keys are rejected as ambiguous. Its expected public value is supplied as an independently authored fixture, rather than generated by the same implementation being checked. No nonce ledger, internal projection trace or particular implementation strategy is required.

## F08: test semantic text preservation

The old observer requires one particular named HTML entity. The prospective acceptance condition is that the badge's existing status span contains the requested label as literal text, without introducing additional elements or attributes. Named and numeric character references that yield the same text must be accepted. DOM/text semantics should determine acceptance rather than the spelling of an entity.

The included observer controls use harmless formatting labels and test named and numeric encodings. They do not execute any browser script or saved implementation. A production replacement must bind the accepted span structure and parser behavior before evaluation.

## Validation boundary

`check_outputs.py` validates these output acceptance rules with hand-authored ordinary output records. It never imports an agent submission, invokes the historical security witnesses, or changes an evaluator in the original evidence tree. Passing these controls establishes that this observer accepts the specified equivalent outputs and rejects the specified contract near misses. It does not establish complete benchmark validity or new agent performance.

For the other eleven families, `data/observer_contract_review.csv` records a completed static inspection of the original observation target and an inventory of distinct saved implementations that passed both historical checks. That inventory is evidence of observed acceptance diversity, not proof that all legitimate algorithms are accepted. A later benchmark revision must validate new alternative implementations and score saved submissions under a separately frozen evaluator version before reporting new results.
