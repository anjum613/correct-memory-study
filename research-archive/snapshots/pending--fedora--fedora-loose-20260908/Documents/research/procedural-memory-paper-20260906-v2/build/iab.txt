                                                         Abstract

 1             A procedure can be correct where it was learned and incomplete where it is reused.
 2             We study coding agents supplied with procedural memory in target tasks that
 3             change a security relevant source assumption. Thirteen synthetic families cross
 4             four memory conditions and two repetitions in six model and agent configurations,
 5             yielding 624 recorded runs and 595 technically valid outcomes. The primary end-
 6             point is functional completion that fails a focal security witness. Correct memory
 7             changes this endpoint by −11.5 to +13.6 percentage points across configurations;
 8             the experiment does not establish a general harmful memory effect. Lower failure
 9             rates sometimes accompany lower functionality. A generic applicability reminder
10             reduces the endpoint descriptively in the three Codex configurations, a direction
11             that survives all assignments of unresolved outcomes in the recorded cohort. Two
12             isolated LLM annotation passes over a sample of 52 runs document procedure re-
13             tention, protection, explicit assumption recognition, and non-completion separately.
14             Protections often appear without preceding explicit recognition in the visible trace.
15             Together, the outcome decomposition and implementation evidence show how
16             non-completion, witness scope, and distinct implementation mechanisms change
17             the interpretation of apparent memory transfer successes and failures.


18   1    Introduction

19   Procedural memory lets an agent reuse a successful method without deriving it again. Yet success is
20   conditional. A record may have been complete before reaching a parser; a cache may have belonged
21   to one request; a diagnostic object may have contained only public fields. If the target changes these
22   assumptions, a memory can accurately describe the source task while providing an incomplete guide
23   to the new one.
24   We ask: when a coding agent receives a source procedure in a target context where its assumptions
25   no longer hold, how does that memory change functional completion and focal security failures?
26   A second question asks whether a generic applicability reminder changes this behavior. We supply
27   a frozen correct memory, a matched irrelevant memory, correct memory with the reminder, or no
28   memory. The target task and changed assumption remain fixed.
29   The original hypothesis was that correct source memory would increase functional completions that
30   violate the target’s focal security property. The completed experiment does not establish this as a
31   general effect. Corrected estimates have both signs across six configurations. This mixed result
32   becomes informative when completion, measurement availability, and implementation behavior are
33   examined together. A lower failure rate can reflect an unfinished task. A witness pass can establish
34   confidentiality without establishing useful output. Two implementations can fail the same witness
35   through different mechanisms.

36   The study contributes (1) thirteen controlled synthetic families with explicit source assumptions and
37   separate functionality and security observations; (2) corrected treatment comparisons, joint outcomes,
38   and bounds that retain completed measurements within otherwise invalid runs; and (3) systematic
39   exploratory coding of a transparently selected 52-run sample, complemented by matched transcript,
40   patch, and outcome comparisons. The coding separates what agents say before editing from the
41   protections they implement. The resulting contribution is a more precise account of observed memory
42   transfer, including successful adaptations and counterexamples to harmful reuse.
43   All targets contain a context shift, and memories are supplied directly. The intervention therefore
44   estimates the effect of supplied memory in those targets; it does not identify the effect of context shift
45   or evaluate a retrieval system. Comparisons are made within each model and agent configuration.


46   2   Related work

47   Memory and applicability. Voyager stores reusable executable skills, while ExpeL extracts natural
48   language lessons from experience without updating model parameters [Wang et al., 2023, Zhao
49   et al., 2023]. These systems motivate procedural reuse, but successful transfer is conditional on
50   what the memory preserves. Kim et al. [2026] study four memory representations across six coding
51   benchmarks and find that abstract insights transfer more reliably than concrete traces. Our experiment
52   fixes a procedure valid at the source and changes its relevance to a target security contract; the
53   endpoint distinguishes task non-completion from a functional security violation.
54   Boundary-Aware Skill Memory (BASM) is the closest applicability-aware method [Lin et al., 2026].
55   It augments skills with applicability conditions, risk cues, avoidance rules, and recovery notes, and
56   combines retrieval, boundary-conditioned execution, and local repair. It also investigates wrong-
57   tool preference using attention and intervention analyses. Our B arm is a single generic reminder
58   attached to a supplied memory. It neither implements BASM nor tests its structured mechanism. The
59   contribution here is a controlled outcome decomposition for coding under changed trust assumptions,
60   together with visible implementation evidence. We do not claim novelty for the general observation
61   that relevant skills can be inapplicable.

62   Skill induced regressions. SWE-Skills-Bench measures the marginal utility of supplied skills in
63   repository software tasks and reports limited average gains and context-compatibility failures [Han
64   et al., 2026]. Dong et al. [2026] use differential analysis of paired runs to examine functional failures
65   and efficiency regressions induced by loaded skills. Their results make clear that procedural guidance
66   can constrain implementation in unhelpful ways. Our focal distinction is between failing to implement
67   a feature and implementing it while violating a separately evaluated security property. Our behavioral
68   analysis separates statements, implementation changes, and measured outcomes.

69   Security and the execution interface. SecureVibeBench reconstructs vulnerability-introducing
70   scenarios in 105 C/C++ tasks from 41 OSS-Fuzz projects and combines functionality and security
71   evaluation [Chen et al., 2026]. We cite its ACL 2026 version, which supersedes the earlier arXiv
72   report. Its repository realism addresses a different objective from our synthetic memory intervention.
73   Experience-driven self-evolution can also trade safety against task utility in web and embodied
74   settings [Zhao et al., 2026]; our measured behavior is the generated implementation rather than
75   refusal of a harmful request. Finally, SWE-agent demonstrates that the agent computer interface
76   affects software engineering performance [Yang et al., 2024]. This matters directly here: different
77   tool surfaces and execution budgets are part of each evaluated configuration, and interface related
78   non-completion changes the meaning of an apparent security pass.


79   3   Task construction and experimental design

80   Source validity and changed assumptions. Each family pairs a source setting where a procedure
81   is valid with a target feature request that changes a relevant assumption. The final suite contains
82   six F-series and seven X-series synthetic families, covering parsing, lifetimes, paths, rendering,
83   identity, confidentiality, and state consistency. Existing baseline code is visible in every condition. N
84   removes supplied memory, not the task’s implementation. Appendix A gives the family contracts and
85   construction records.

86    Reference controls. The saved preflight checks three target states in each family: the incomplete
87    baseline must fail functionality and pass the focal witness; an unadapted functional reference must
88    pass functionality and fail the witness; and a repaired reference must pass both. Thus avoiding the
89    requested feature is insufficient for success. The final manifest fixes the synthetic artifacts and source

92    alternative implementations requires examining what the observer actually measures.

93    Configurations and execution. The six configurations each complete their 104-run schedule,
94    producing 624 recorded runs: 595 technically valid and 29 invalid. Codex and MiniSWE have
95    different native interfaces, instruction envelopes, and budgets. Requested aliases are preserved;
96    backend identities are not inferred. Executed manifests record run order. Appendix C gives the scope

98    Memory conditions. The conditions are no memory (N), correct source memory (C), matched
99    irrelevant memory (I), and correct source memory with a generic applicability boundary (B). C, I,

102   repair. C−N is the frozen primary contrast; I−N and B−C are secondary.

127   4   Results
128   Correct memory has no established common harmful effect. Table 2 gives the corrected compar-
129   isons. C−N changes U by +9.1, +13.6, and +4.2 percentage points for GPT-5.5, Luna, and Terra,
130   and by 0.0, −11.5, and −4.2 for Qwen Next, Qwen 30B, and Devstral. The signs differ, and every
131   C−N bootstrap interval includes zero. The original hypothesis is therefore not established across the
132   evaluated configurations.

133   Joint outcomes distinguish improvement from non-completion. For Qwen 30B, C−N lowers U
134   by 11.5 points and functionality by 15.4 points. Across its thirteen eligible families, functional runs
135   fall from 24 to 20 out of 26, and functionality and focal witness passes fall from 8 to 7. This is not an
136   improvement that preserves functionality. Devstral’s U also falls, by 4.2 points, while functionality
137   rises by 4.2 points. Identical endpoint directions can describe different changes in performance.
138   Figure 1 retains all recorded runs. Qwen Next has 38 valid ¬F ∧ S outcomes, all with unchanged
139   final implementations in the saved audit. Luna has 18 such outcomes; sixteen have empty patches and
140   visible complaints about unavailable named tools. These observed non-completions make a security
141   pass rate alone misleading.

142   The reminder reduces observed failures in Codex. B−C lowers U by 30.0, 13.6, and 22.7 points
143   in the three Codex configurations. Functionality is unchanged for GPT-5.5 and Terra and rises by 4.5
144   points for Luna. MiniSWE estimates are 0.0, +4.2, and 0.0 points. The distinction concerns complete
145   configurations, including their interfaces. None of the C−N or B−C exact family sign flip diagnostics
146   is below .05. GPT-5.5’s B−C bootstrap interval excludes zero, whereas its sign flip diagnostic is
147   .125; few families have nonzero differences and the procedures make different assumptions.

167   5   Exploratory behavioral analysis

168   Sampling and coding. We froze a four-dimension codebook and sampled one run from every
169   family and condition cell, giving 52 runs. Configuration assignments were shuffled and balanced to
170   eight or nine runs each; a repetition was selected at random. Selection used design labels, without
171   outcomes or trace availability, and no run was replaced. All 52 selected traces and implementations
172   were available. Two isolated LLM sessions independently read every packet, with final scores and
173   model labels withheld. Each packet contained the task, a source procedure for comparison, the initial
174   implementation, chronological visible statements and tool interactions, and the final implementation
175   and patch. Tool interfaces and public feedback remained visible.
176   The dimensions distinguish explicit recognition of the changed source assumption before editing
177   (A), retention of a recognizable source procedure without its target check (P), a concrete target
178   protection (T), and stopping without a meaningful implementation (Z). Each decision includes event
179   or implementation line anchors. Labels are yes, no, uncertain, and unavailable. The passes could not
180   inspect each other’s output; disagreements were retained without outcome based adjudication. This is
181   automated exploratory coding, separate from the earlier casebooks selected after outcome inspection.

182   Expressed recognition and implemented protection are distinct observations. Both passes
183   identify explicit recognition before editing in 7 runs, procedure retention without the check in 20,
184   concrete protection in 22, and no meaningful implementation in 7 (Table 4). All seven runs with
185   agreed explicit recognition also have agreed protection. Fifteen further runs have agreed protection
186   without agreed explicit recognition. This difference demonstrates why absence of an explanatory
187   statement cannot be used as evidence that memory was ignored.
188   The sampled Luna F08/B/r2 run (P027) illustrates the timing distinction: its patch escapes the label,
189   but the visible explanation follows the edit. The saved outcome passes both checks. In Devstral
190   X20/C/r1 (P015), recognition does precede editing: the agent distinguishes newly repeatable tags
191   from a control field that remains singular, then rejects duplicate controls and uses one interpretation
192   for authorization and dispatch. Both checks pass. The codebook captures these different observable
193   paths to protection without attributing either edit causally to the statement.
194   Protection codes also differ from outcome scores. Terra X28/B/r1 (P043) explicitly recognizes that
195   a positive prefilter result is insufficient and adds an authoritative check. Both passes code A and
196   T positively. Functionality evaluation completes successfully, but the error path interrupts security
197   measurement, leaving the run invalid. A plausible main path repair is therefore documented without
198   assigning an unobserved security result.

219   6   Measurement implications and discussion
220   Observe useful behavior as well as confidentiality. We reviewed the observation contract in
221   all thirteen families against the saved observers and accepted implementations (Appendix G). The
222   X05/X28 corrections show why three reference controls were insufficient: alternative implementations
223   exposed dependence on optional bookkeeping. The review also identifies a representation constraint
224   in F08’s literal entity check and an unspecified useful output obligation for X06’s mixed record.
225   We specify prospective output contracts separately from the executed evaluation. For X06, supported
226   public fields must survive the mixed record; unsupported public scalar values become null, and
227   unsupported private fields are omitted without conversion. Confidentiality and required public output
228   receive separate labels. For F08, named and numeric entities representing the same literal label are
229   equivalent. Fourteen benign output controls pass these new observer checks, including rejection
230   that preserves confidentiality but fails useful output. These controls test the proposed observers, not
231   saved agent implementations; no historical score changes. The complete policy and family review are
232   included in the artifact.

233   A focused next experiment. Memory supplies both a procedure and information about its pre-
234   conditions. The F08 comparison motivates separating those components. A prospective protocol
235   in the artifact compares no memory, procedure only, source assumption only, and both, holding the
236   target fixed and avoiding a target repair in the assumption text. It specifies interface qualification,
237   randomized execution order, and a precision plan before a new cohort. This follow-up has not been
238   run.

239   Limitations. Thirteen selected synthetic families and two repetitions provide limited precision and
240   do not sample repository work. Witnesses cover specific properties; the observer review is static,
241   and the new output controls do not exhaust legitimate implementations. The 52-run coding is an
242   exploratory sample assessed by two LLM contexts that may share biases, with imperfect model

243   masking and eight retained disagreements. It supplies inspectable observations, not human validated
244   labels or causal mediation. Memory retrieval, the context shift interaction, and differences attributable
245   to model weights remain outside the design.

246   7   Conclusion
247   The experiment does not establish a general harmful memory effect. Its strongest findings concern
248   how non-completion, witness scope, and implementation evidence change the interpretation of
249   apparent transfer successes and failures. Joint outcomes separate unfinished work from functional
250   security failures; bounds expose the consequences of missing measurement; and systematic trace
251   coding distinguishes expressed assumptions from implemented protections. These distinctions make
252   the mixed result scientifically useful without requiring a stronger claim than the evidence supports.
