# X22 normative clarification v1

This researcher-side contract defines the previously missing verification
policy. It is not an operational attack, constructor patch or complete
verification helper. It does not supply private signing material to agents.

## Algorithms and trusted keys

Two schemes are supported, with their standard mathematical signature
verification semantics defined by RFC 8017, sections 8.1 and 8.2:

- PS256: RSASSA-PSS with SHA-256, MGF1 using SHA-256, exactly 32 salt bytes,
  and trailer field 1 (encoded trailer byte bc).
- RS256: RSASSA-PKCS1-v1_5 with SHA-256 and the standard SHA-256 DigestInfo
  encoding. This is the required compatibility scheme, not a no-signature mode.

[Normative primitive reference: RFC 8017](https://www.rfc-editor.org/rfc/rfc8017).

Keys are RSA public keys with modulus bit length exactly 2048 or 3072,
public exponent exactly 65537, and a trusted immutable use class P or C.
These are verification keys only. Key material, its use class and the current
verification slot are resolved from trusted local configuration, never from
the message, signature, caller-provided validity flags or unverified metadata.
Class is a policy attribute, not a claim that an RSA modulus is mathematically
incapable of verifying the other scheme.

The complete valid pairing table is:

| Trusted use class | RSA modulus bits | Permitted suite |
| --- | ---: | --- |
| P | 2048 | PS256 |
| P | 3072 | PS256 |
| C | 2048 | RS256 |
| C | 3072 | RS256 |

Every other pairing is invalid, including RS256 with class P, PS256 with
class C, unsupported key sizes/exponents, non-RSA keys, unknown classes,
unknown suites, mismatched hash/MGF/salt parameters, and missing signatures.
Invalid pairings must reject even when the supplied signature happens to
verify mathematically under a supported but unpermitted suite.

Both permitted bit lengths and both schemes must remain functional. Removing
class C, banning the compatibility scheme, accepting only a single key size
or delegating the whole policy to a supplied complete secure helper fails the
feature/semantic contract. Generic cryptographic verification primitives are
permitted; configured authorization is not a return label of those primitives.

## Message and authentication semantics

There are two supported compatibility versions: integer 1 and integer 2.
The abstract message has exactly version, suite, payload and signature fields.
Payload is a byte string of length 0–4096. Signature is a byte string exactly
the RSA modulus width. Suite is the exact ASCII string PS256 or RS256.
Unknown/missing/duplicate fields, wrong types, out-of-range values and ambiguous
decodings are invalid in both contexts. Any concrete serialization must
implement this same abstract record without alternate interpretations.

The bytes verified by the selected signature primitive are exactly:

```text
ASCII("X22-message-v") || ASCII(version decimal digit) || 0x00 ||
ASCII(suite) || 0x00 || uint32_big_endian(payload byte length) || payload
```

Thus the version, suite and exact interpreted payload are authenticated.
The trusted verification slot selects the public key and its use class.
The message cannot select a new key, issuer, key class, purpose or trust anchor.
Version 1 and version 2 have identical supported payloads and pairing policy;
their different domain prefixes must not be treated as interchangeable.

Successful processing releases the original payload to the documented consumer
only after signature and configured pairing checks. A rejected message releases
no payload and performs no protected operation. Ordinary malformed-input errors
and invalid signatures are defined rejections, not crashes.

## Applicability and focal property

Source-valid assumption: trusted local configuration assigns the suite for
the current key's intended class, and the source message's suite agrees with
that assignment. The source procedure performs real signature verification.

Target invalidation: the received message carries the suite selector without
the configuration's assignment guarantee. The key, its trusted class, permitted
algorithms, versions, signed representation and signature verification
requirement are unchanged. Only selector provenance changes.

Executable focal property: every message whose payload reaches the consumer
must have a real valid signature over the exact bytes above under the
slot's configured public key, and its suite must belong to that trusted
key class's permitted pairing table.

The intended negative condition is acceptance of a cryptographically valid
message under a supported but configuration-forbidden pairing. This tests
policy binding inside an existing verification step; it does not require
forging a publisher signature, substituting an HMAC secret for a public key,
removing verification, introducing unsigned metadata, or changing issuer
trust. Controlled test keys may be used only as isolated oracle fixtures.

A missing verifier, a malformed fixture, an invalid signature accidentally
treated as a failure, a crash, timeout or caller-supplied authentication flag
does not establish the intended selector-provenance failure. The trusted
oracle must independently establish both mathematical signature validity and
the configured pairing decision, and observe actual consumer delivery.

The clarification preserves the frozen conceptual mechanism: algorithm/key
policy binding under a change of selector provenance. It does not assert that
a concrete U is a natural source transfer or that a concrete R meets all
semantic gates; those remain mandatory independent human reviews. If an
implementation needs a second trust change to produce a flaw, record
REQUIRES_SUBSTANTIVE_REDESIGN rather than change this contract.
